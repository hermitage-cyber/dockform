# Выпуск релиза

Инструкция, как собрать новую версию портативного `dockform.exe` и раздать её пользователям. Релиз делается редко (по мере накопления правок кода), идём строго по шагам.

Это **portable**-workflow: устанавливать ничего не нужно, файл запускается с флешки или из любой папки. Автообновление приложения через `tauri-plugin-updater` в текущем дистрибутиве **отключено** (см. ниже «Почему без автообновлений»), поэтому ключи подписи и `latest.json` не используются.

## Когда выпускать релиз

- Закончен этап разработки из `plan.md` (например, Этап 8 → выпуск v0.8.0).
- Накопились правки кода (НЕ шаблонов — для шаблонов релиз приложения не нужен, см. `template-authoring.md`).
- Срочная правка критичного бага.

**НЕ выпускать релиз только ради:**
- Изменения шаблонов или справочников — они доставляются через `manifest.json` отдельно, без пересборки приложения.
- Изменения `killswitch.json` — он читается напрямую с GitHub.

## Версионирование

Семантическое: `MAJOR.MINOR.PATCH`.
- **MAJOR** — несовместимые изменения формата шаблонов или конфигурации (потребует ручных действий от пользователей).
- **MINOR** — новые возможности, совместимые со старыми шаблонами.
- **PATCH** — багфиксы.

Первая раздача пилотам — **v1.0.0**. Дальше PATCH на фиксы, MINOR на новые возможности.

## Порядок при правках кода: сначала .exe, потом шаблоны

**Правило.** Если в изменении затронуты калькуляторы (`src/lib/calculators/`), валидатор
(`src/lib/template-validator.ts`, `src/lib/wizard-validator.ts`) или формат `.yaml` — это
несовместимое изменение контракта шаблонов. Сначала собрать и раздать `.exe`, потом пушить
шаблоны, которые на него опираются.

Почему: шаблоны обновляются автоматически с GitHub, а `.exe` раздаётся руками. Разъехавшись, они
дают ровно то, что видел пилот 2026-08-10 — «Шаблон настроен некорректно: outputs: лишние ключи»
и неоткрывающуюся форму (разбор: `docs/отзыв-пилота-2026-08-10.md`).

Правки только текста в `.docx` этого не требуют: пересчитать манифест, закоммитить, пилот
получит их при следующем запуске. Это основной и самый частый случай.

Версия сборки видна пилоту — в правом нижнем углу окна (`src/components/StatusBadge.tsx`),
там же кружок состояния шаблонов.
Просить скриншот с ней, если что-то ведёт себя странно: до v1.0.0 версия не менялась ни разу
за 41 коммит, и по одному номеру `0.1.0` нельзя было отличить майскую сборку от июньской —
именно поэтому причину сбоя у пилота искали вслепую.

## Гейт совместимости (`min_app_version`)

В `manifest.json` можно положить поле `min_app_version`. Приложение сверяет его со своей версией
(`app_is_compatible` в `src-tauri/src/commands/manifest.rs`): если оно старее — синхронизация
шаблонов пропускается целиком, на диске остаётся то, что работало, а фронт показывает плашку
«Обновите dockform.exe: новые шаблоны требуют версию N, у вас M» вместо технической ошибки.

**Поле ставится руками и редко.** `scripts/build_manifest.py` его не генерирует — только
переносит, если оно уже есть в манифесте. Автоматическая простановка (версия из `package.json`
при каждом прогоне) пробовалась и откачена: гейт всё-или-ничего замораживал доставку шаблонов
всем, кто ещё не получил новый `.exe`, включая правки чистого текста, которые на старой сборке
отработали бы нормально.

**Сейчас стоит `min_app_version: "1.0.0"`.** Причина: калькулятор `invoice_transfer_deadline`
(срок передачи счёта в ОГЗ) появился только в 1.0.0, а `.yaml` шаблонов на него уже ссылаются.
Пилот на сборке `0.1.0` без гейта получил бы «лишние ключи» ровно как 2026-08-10; с гейтом он
остаётся на своих шаблонах и видит просьбу обновиться.

Гейт снимать не надо — он перестанет срабатывать сам, когда у всех будет 1.0.0 или новее.
Поднимать значение снова следует при следующем несовместимом изменении контракта, в том же
порядке: поднять версию → выставить `min_app_version` руками → запушить → собрать и раздать
`.exe`. Отсутствие поля означает «совместимо с любой версией».

## Подготовка

### Шаг 1. Проверить, что всё работает

1. `npm run tauri dev` — приложение запускается без ошибок в консоли.
2. Прогнать чеклист текущего этапа из `plan.md`.
3. Дымовой тест: выбрать шаблон (или пройти анкету в режиме претензий), заполнить, сохранить — документ создаётся корректно и открывается в Word.
4. Если в этом релизе менялись сетевые функции (kill switch, обновление шаблонов) — проверить с включённым и выключенным интернетом.

Если что-то не работает — НЕ выпускать релиз, доделать.

### Шаг 2. Bump версии

Версия указана в трёх местах, они должны быть синхронны:

```
package.json              → "version": "1.0.1"
src-tauri/Cargo.toml      → version = "1.0.1"     (под [package])
src-tauri/tauri.conf.json → "version": "1.0.1"
```

Поправить руками во всех трёх. После правки:

```bash
git add package.json package-lock.json src-tauri/Cargo.toml src-tauri/Cargo.lock \
        src-tauri/tauri.conf.json
git commit -m "Bump версии до 1.0.1"
```

Bump версии сам по себе на доставку шаблонов не влияет — гейт `min_app_version` выставляется
отдельно и руками, см. «Гейт совместимости».

### Шаг 3. Обновить «Текущий этап» в CLAUDE.md

Раз с релизом меняется этап разработки — поправить секцию «Текущий этап» в `CLAUDE.md`, чтобы Claude Code в следующих сессиях знал, на чём сосредоточиться.

```bash
git add CLAUDE.md
git commit -m "CLAUDE.md: обновлён текущий этап"
git push
```

## Сборка

### Шаг 4. Собрать на Windows-машине

Сборка под Windows — на Windows. Кросс-компиляция с macOS/Linux не поддерживается официальным toolchain'ом Tauri и в этом проекте не используется.

На рабочей Windows-машине с установленными Rust, Node.js, npm, Visual Studio Build Tools:

```bash
git pull
npm install
npm run tauri build
```

Сборка займёт 3–10 минут (Rust компилируется небыстро при первом разе и при больших изменениях).

После успешной сборки портативный бинарь лежит здесь:

```
src-tauri/target/release/dockform.exe
```

Это и есть наш portable. В папке `src-tauri/target/release/bundle/` Tauri дополнительно положит NSIS-инсталлятор и MSI — мы их **не используем** для распространения, можно игнорировать или удалить.

### Шаг 5. Локальная проверка сборки

1. Скопировать `dockform.exe` в отдельную пустую папку вне репозитория.
2. Рядом — папки `templates/` и `dictionaries/` (просто скопировать соответствующие каталоги из репо).
3. Запустить `dockform.exe`. Должно открыться окно. Проверить базовый сценарий: выбор шаблона / анкета → заполнение → генерация документа.
4. Если работает — продолжаем. Если нет — расследовать, не выпускать.

## Подготовка папки распространения

### Шаг 6. Собрать финальную папку

Структура того, что отдаём пользователям:

```
dockform/
├── dockform.exe
├── README.txt                (копия docs/portable-README.txt)
├── templates/
│   ├── pretenzii/
│   └── documentation/
├── dictionaries/
├── cache/                    (пустая, для черновиков формы и сетевых кэшей)
└── output/                   (пустая, для готовых .docx)
```

> **Ярлыков `.lnk` в папке нет** — от них отказались в v1.0.0. Запуск всегда
> через `dockform.exe`, раздел выбирается на первом экране. Ярлыки прокидывали
> `--mode=...` и уводили мимо экрана выбора, а вместе с ним — мимо индикатора
> состояния шаблонов. Оставшиеся у пилотов `.lnk` от прошлых сборок программа
> удаляет сама при старте (`src-tauri/src/commands/shortcuts.rs`).

Собирается скриптом — руками копировать не надо:

```powershell
.\scripts\build_portable.ps1 -Zip
```

Результат: `dist\dockform\` и `dist\dockform_1.0.0.zip`. Папка `dist/` в `.gitignore`,
в репозиторий не попадёт.

Флаги: `-Build` — сначала выполнить `npm run tauri build` (тогда шаг 4 отдельно не нужен);
`-Zip` — упаковать архив; `-OutDir` — сложить в другое место.

**Что скрипт проверяет за тебя:**
- версия `.exe` совпадает с `package.json` — иначе останавливается. Это защита от сборки без
  `git pull`: в августе 2026 так собрали и чуть не раздали `0.1.0`, когда в репозитории было
  `1.0.0`;
- `manifest.json` не старее шаблонов (иначе предупреждает — надо прогнать `build_manifest.py`);
- `.exe` собран не сутки назад — на случай, если забыл пересобрать.

**Что он исключает из `templates/`:** папку `old/` (архив старых редакций, 13 файлов),
`.md`-заметки разработчика, `~$`-блокировки Word и скрытые файлы. Списки исключений намеренно
совпадают с `scripts/build_manifest.py` — если развести их, у пилота на диске окажутся файлы,
которых нет в манифесте.

Если по какой-то причине надо руками: создать `dockform/`, положить `dockform.exe` из
`src-tauri/target/release/`, скопировать `templates/` и `dictionaries/` (без `old/` и `.md`),
создать пустые `cache/` и `output/`, положить `docs/portable-README.txt` как `README.txt`.

### Шаг 7. Упаковать в zip

Уже сделано флагом `-Zip` на прошлом шаге. Отдельно, если нужно:

```powershell
Compress-Archive -Path dist\dockform -DestinationPath dist\dockform_1.0.0.zip
```

Внутри архива должна оказаться одна папка `dockform/` со всем содержимым. Проверить:
```powershell
Expand-Archive -Path dockform_1.0.0.zip -DestinationPath проверка\
dir проверка\dockform
```

## Раздача

### Шаг 8. Доставить пользователям

Способы (выбрать удобный):
- Положить `dockform_1.0.0.zip` на общий сетевой ресурс / Google Drive / Dropbox, разослать ссылку.
- Записать на флешки, раздать лично.
- Отправить почтой (если размер позволяет).

Сопроводить коротким сообщением:
- Распаковать архив в любую папку (Документы, флешка, рабочий стол — без разницы).
- Запускать `dockform.exe` двойным кликом, раздел выбирается на первом экране.
- Старые ярлыки «Претензионная» / «Документация», если остались от прошлой
  сборки, программа удалит сама — пользоваться ими больше не нужно.
- В правом нижнем углу — версия и кружок состояния шаблонов. Просить скриншот
  вместе с этим углом, если что-то пойдёт не так.
- Если программа не открывается — см. `README.txt` в папке.

### Шаг 9. Создать тег в репозитории

Для истории и удобства поиска версии:

```bash
git tag v1.0.0
git push origin v1.0.0
```

Префикс `v` — обязательно.

Опционально создать GitHub Release с тегом и приложенным zip-архивом — это удобно как зеркало для пользователей, у которых пропала локальная копия. Через `gh`:
```bash
gh release create v1.0.0 dockform_1.0.0.zip \
  --title "v1.0.0 — первая раздача пилотам" \
  --notes "Список изменений..."
```

## Почему без автообновлений

В реализации этапа 6.3 (`plan.md`) подключён `tauri-plugin-updater`, но в текущем дистрибутиве он **не используется**:
- В `tauri.conf.json` стоит `"createUpdaterArtifacts": false` — `.sig` и `latest.json` не создаются.
- `pubkey` в `plugins.updater` оставлен заглушкой (`REPLACE_BEFORE_FIRST_RELEASE`) — реальный ключ не сгенерирован.
- При запуске фронт вызывает `check()` (см. `src/App.tsx`), но без валидной пары ключ/`latest.json` вызов завершается ошибкой, которая ловится в `try/catch` и просто пишется в `console.warn` — UI не блокируется.

Причины такого решения для пилотной версии:
- Целевая аудитория — 5–10 сотрудников, новую версию проще доставить лично или общим ресурсом.
- Portable-сценарий (exe рядом с папкой `templates/` на флешке) плохо сочетается со стандартной моделью `tauri-plugin-updater`, рассчитанной на установленное приложение в `Program Files`.
- Удалённая блокировка (`killswitch.json`) и обновление шаблонов остаются — критичные защитные механизмы работают.

Если в будущем понадобится автообновление приложения — порядок включения:
1. Сгенерировать пару ключей: `npm run tauri signer generate -- -w ~/.tauri/dockform.key`.
2. Вставить публичный ключ в `src-tauri/tauri.conf.json` → `plugins.updater.pubkey`.
3. Поменять `bundle.createUpdaterArtifacts` на `true`.
4. Переключить распространение с portable zip на NSIS-инсталлятор (`bundle/nsis/*.exe`), либо разобраться, как updater работает поверх portable-папки (нетривиально).
5. Каждый релиз — выгружать на GitHub Releases `latest.json`, `.nsis.zip` и `.sig`.

Подробности — этап 6.3 в `plan.md`.

## Откат

Если выпустили битый релиз и архив уже у пользователей:

1. Сообщить пилотам, что текущая версия проблемная (мессенджер / телефон), попросить временно не пользоваться.
2. На случай удалённой блокировки можно поднять флаг в репозитории:
   ```json
   // killswitch.json
   { "active": false, "message": "Версия 1.0.0 содержит ошибку, ждите обновление." }
   ```
   Закоммитить и запушить. При следующем запуске у пользователей экран блокируется.
3. Быстро собрать фикс-версию (bump до следующего patch — например, 0.9.1), повторить релиз.
4. Снять флаг блокировки и раздать новый архив.
